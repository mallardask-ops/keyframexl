# P5 — Світла тема та налаштування тулбару

Дослідження до `docs/v0.2.0.md` → P5. Стан коду: v0.1.2 (листопад 2026),
`eframe`/`egui` 0.31.1, `winit` 0.30.13 (вендорений). Нижче — інвентар того,
що є, дві палітри з перевіреними коефіцієнтами контрасту, схема перемикання
на льоту, спосіб дізнатися системну тему на Linux і модель налаштування
тулбара. Оцінки трудомісткості — для однієї людини з агентами.

## Коротко

- **68 кольорових токенів** (`src/theme.rs`, 70 `pub const` разом із двома
  масивами) і **1352 звернення** до них у 26 файлах `src/`. Токени — `const`,
  тому перемикання на льоту потребує зміни типу доступу, а не лише другої
  таблиці кольорів.
- Поза `theme.rs` — **76 літералів кольору** у 9 файлах (45 з них — один
  `fx_views.rs`), **127 викликів `gamma_multiply`** (ідіома «притемнити до
  фону», чинна тільки на темному) і **~45 місць**, де темні «фейсплейти»
  Tide/Sampler змішуються з глобальним чорнилом (`t::TEXT`, `t::MUTED`).
- Рекомендована схема: два `static Palette` + `AtomicU8` і аксесори
  `t::text()`. Замір: **0,7 нс** на читання (інлайн) / 2,7 нс (без інлайну);
  `ArcSwap` — 15 нс, тобто в 10–20 разів гірше без жодної переваги.
- Світла палітра: 68 значень, усі текстові пари ≥ 4,5:1 (WCAG AA), «холодний
  верстатний сірий» замість чистого білого; глибина тримається на шві
  (`EDGE`), бо тональні сходинки у світлій темі неминуче ≤ 1,25:1.
- Системну тему **на Linux winit не віддає** (`system_theme()` → `None`,
  X11 `window.theme()` → `None`, `ThemeChanged` не приходить), тому
  «системна» = запит до `org.freedesktop.portal.Settings`
  (`color-scheme`: 0/1/2). `ashpd` 0.11.1 уже в `Cargo.lock` (через `rfd`),
  але дешевше й достатньо — одноразовий `gdbus call`.
- Тулбар: 11 блоків у двох рядах (82 px), з них 1 закріплений (транспорт);
  модель — `DeckSettings { row1, row2, hidden }` у `settings.ron`, висота
  панелі стає функцією від налаштувань (економія 34 px за прибраний ряд 2).
- Разом ≈ **26–40 год** роботи, з яких 8–12 — механіка (аксесори + літерали),
  6–8 — світла палітра й контраст, 8–12 — тулбар і системна тема.

### 1.4 Темні ідіоми, які зламаються

**`gamma_multiply` як «притемнити».** 127 викликів у 17 файлах
(`synth` 38, `fx_views` 23, `sampler` 21, `roll` 15, решта 30). На темному
`c.gamma_multiply(0.45)` = «послабити до фону». На світлому множник робить
колір **темнішим**, тобто лінія сітки стає контрастнішою за саму сітку:

| Місце | Зараз | У світлій темі |
|---|---|---|
| `automation.rs:668`, `fx_views.rs:163`, `tempo_lane.rs:177` | `t::LINE.gamma_multiply(0.45)` — ледь видима сітка | `#C6CBD1 → #595B5E`: темна жирна лінія |
| `fx_views.rs:236,250` | `t::MUTED.gamma_multiply(0.22/0.7)` — заливка/обвід | чорні плями |
| `fx_views.rs:403` | `t::SUNKEN.gamma_multiply(0.85)` — «глибше дна» | майже чорний прямокутник |
| `files.rs:493` | `t::RAISED.gamma_multiply(0.6)` — плитка | темна плитка |
| `status_bar` | `ink.gamma_multiply(pulse)` — пульс лампи | пульс у чорне замість «згасання» |

Правильна заміна — `kit::mix(c, surface_під_ним, 1.0 - k)`, тобто згасання
**до фону**, а не множення. Це не механічна заміна: у кожного місця свій фон
(панель, дно, рядок ноти).

**Фейсплейти.** `synth.rs` малює на `TIDE_CHASSIS #12171C` текстом
`t::TEXT` (12 разів: `:313,370,439,661,780,925,1242,1480,1834,1885,1925,3107`),
`t::MUTED` (`:216`), `t::FAINT` (`:676,796,1490,1885,1925,1953`),
`t::STRONG` (`:639,763,1224,1275,1500,2969`), лінії `t::EDGE` (`:239,293,1611,1666`).
`sampler.rs` — те саме (`:341,451,655,851,1210,2690` тощо). Якщо ці токени
перевернути, усередині інструментів з'явиться темне чорнило на темній
пластині.

**Оверлеї.** `mod.rs:3073` малює чорний скрим `alpha 140`, а `:3084` —
напис `t::TEXT`. У світлій темі це темний текст на затемненому екрані.
`roll.rs:1706` — те саме для затінення під час виділення.

## 2. Архітектура перемикання

### 2.1 Варіанти

| Варіант | Як | Міграція call-sites | Ціна читання (замір) | Вирок |
|---|---|---|---:|---|
| **A. `&'static Palette` + `AtomicU8`** | два `static` структури, `p()` вибирає за атоміком, `t::text()` — тонкий аксесор | 1352 механічні заміни `t::TEXT` → `t::text()` | **0,7 нс** інлайн / 2,7 нс без | **обрати** |
| B. `ArcSwap<Palette>` | `static SWAP`, `SWAP.load().text` | те саме | **15 нс** | у 10–20× дорожче, переваг нема (два стани, не довільна кількість) |
| C. `thread_local! Cell<&'static Palette>` | те саме, але на потік | те саме | ~1 нс | має сенс, лише якщо малювання колись піде з головного потоку — зараз не йде |
| D. `Palette` через `ctx.data` / `Ui` | `t::of(ui)` | кожен painter-only хелпер отримує `&Ui` | — | відкинути: `kit.rs` малює з `&Painter`, `Ui` там немає |
| E. тільки `egui::Visuals` | `ctx.set_visuals` | 0 | — | недостатньо: `Visuals` не знає про бренд, ноти, графіки, фейсплейти |

`ArcSwap` спокусливий, бо він уже є в проєкті (`arc-swap 1.7`, знімки
`Song`), але 15 нс × ~5000 читань на кадр = 75 мкс на кадр (0,45 % бюджету
16,7 мс) проти 3,5 мкс у варіанта A. Для двобарвної палітри це чиста втрата.

### 2.2 Обрана схема

```rust
// src/theme.rs
#[derive(Clone, Copy)]
pub struct Palette {
    pub edge: C, pub sunken: C, /* … усі 68 полів … */
}
pub static DARK: Palette = Palette { edge: C::from_rgb(4,5,5), /* … */ };
pub static LIGHT: Palette = Palette { edge: C::from_rgb(0x9A,0xA1,0xA9), /* … */ };

static ACTIVE: AtomicU8 = AtomicU8::new(0); // 0 = dark, 1 = light

#[inline]
pub fn p() -> &'static Palette {
    if ACTIVE.load(Ordering::Relaxed) == 1 { &LIGHT } else { &DARK }
}
pub fn set(theme: egui::Theme) {
    ACTIVE.store(matches!(theme, egui::Theme::Light) as u8, Ordering::Relaxed);
}

// аксесори: одне ім'я = один токен
#[inline] pub fn text() -> C { p().text }
#[inline] pub fn bg() -> C { p().bg }
```

Чому структура, а не масив чи мапа: **компілятор змушує заповнити обидві
палітри**. Забутий у світлій темі токен — помилка збірки, а не сюрприз у
скріншоті. Масиви `[C; N]` з індексами такого захисту не дають.

Чому `static` із `Color32::from_rgb`: `from_rgb`, `from_rgba_premultiplied` і
`from_black_alpha` — `const fn` (`ecolor-0.31.1/src/color32.rs:94,105,146`),
тому палітри легальні у `static`. `from_white_alpha` **не** `const` (`:151`) —
для `HI` писати `C::from_rgba_premultiplied(178,178,178,178)`.

Чому `AtomicU8`, а не `Cell` у `OnceCell`: `Relaxed`-читання — це одне
завантаження з передбачуваним переходом; жодних блокувань на гарячому шляху
малювання нотаток і падів.

### 2.3 Міграція call-sites

1352 звернення механічні. Скрипт генерує заміни **з самого `theme.rs`**, щоб
не зачепити чужі `t::` (у коді є `Sort::ALL`, `Rect::NOTHING`,
`SampleFormat::F32`, `kit::TOOL_H` — вони виглядають як `t::…` для
необережного regex):

```sh
names=$(grep -oE '^pub const [A-Z][A-Z0-9_]+' src/theme.rs | awk '{print $3}' \
        | grep -vxE 'PATTERN_CODES|COLOR_PALETTE')
for n in $names; do
  l=$(printf %s "$n" | tr 'A-Z' 'a-z')
  grep -rlE --include='*.rs' "\\bt::$n\\b" src \
    | xargs -r sed -i -E "s/\\bt::$n\\b/t::$l()/g"
done
```

Перевірено: у `const`-контекстах токени не зустрічаються (єдині винятки —
сам `theme.rs`: `LCD_ON = TEXT`, `PATTERN_CODES`, `COLOR_PALETTE`), тому
заміна не ламає константи. Вручну лишаються:

- `PATTERN_CODES` (4 звернення, усі в `sampler.rs`) → `t::pattern_codes()`
  або наявний `t::pattern_code(id)`;
- `COLOR_PALETTE` (2 звернення) → `t::color_palette() -> &'static [C; 10]`;
- локальні `const LIT_PAD_TOP/BOTTOM` (`rack.rs:24-25`) і
  `MINT/PAPER` (`riff_machine.rs:193-194`) — переносяться в токени.

**Порядок безпеки:** перший коміт — самі аксесори, що повертають темні
значення. Нульова зміна вигляду, 1352 заміни, перевірка наявними
capture-хуками (`KFXL_CAPTURE`, `src/ui/script.rs`). Лише другим комітом
додається `LIGHT` і перемикач.

| `const` (сьогодні) | 0,04 |
| аксесор + `AtomicU8`, інлайн | **1,42** |

| `ArcSwap::load()` | 30,2 |

`const` «безкоштовний» лише тому, що значення вшивається в інструкцію; 1,4 нс
на пару — це 0,7 нс на колір. Найгірячіше місце — Piano Roll: ~200 нот ×
4 кольори + сітка ≈ 1–2 тис. читань на кадр; разом із мікшером і деком —
стеля ~5 тис. → **3,5–13 мкс на кадр (0,02–0,08 %)**. Тобто перемикання
палітри невидиме для бюджету кадру; оптимізувати нічого.

### 2.5 `Visuals` і дві школи

`setup()` розділити на `setup(ctx)` (шрифти, один раз) і `apply(ctx, theme)`
(стиль + `Visuals`), який викликається на старті й на кожну зміну теми:

```rust
pub fn apply(ctx: &egui::Context, theme: egui::Theme) {
    set(theme);                       // палітра
    ctx.set_theme(theme);             // egui резолвить style_of
    for th in [egui::Theme::Dark, egui::Theme::Light] {
        set(th);                      // збудувати стиль саме з цієї палітри
        ctx.set_style_of(th, build_style(th));
    }
    set(theme);
}
```

Два підводні камені:

1. `set_style`/`set_visuals` пишуть **лише в стиль поточної теми**
   (`context.rs:1880`, `1947`), тому будувати треба явно через
   `set_style_of` для обох — інакше після перемикання egui віддасть
   дефолтний світлий стиль без наших рамок і відступів.
2. `ctx.set_theme(System)` лишає резолв за egui, а на Linux `system_theme`
   завжди `None` (див. §4). Тому краще **самим** резолвити режим у
   `Dark|Light` і ставити `ctx.set_theme` конкретним значенням; `System`
   у egui не використовувати взагалі.

## 3. Світла палітра

### 3.1 Звідки форма

- **Teenage Engineering OP-1 field** — весь корпус, клавіші й ручки одного
  холодного світло-сірого; колір лишається тільки на чотирьох енкодерах
  (адреса, не статус). Це рівно та логіка, що вже в `ui-rules.md`
  («color = address»). Див. огляди нижче.
- **BMS design kit** (першоджерело темної теми) — та сама ієрархія поверхонь
  у світлому варіанті: полотно → панель → піднятий контрол.
- **Ableton Live 12** — офіційні теми з `Follow System`, окремими
  «Tone (cool/neutral/warm)» і `High contrast`; тобто індустрія визнає
  світлу тему як окремий, а не інвертований, дизайн.
- **FL Studio** — редактор тем із ручками `Hue/Saturation/Brightness/Contrast/Text`
  і прапорцем `Light mode` («щоб елементи лишалися видимими при екстремально
  світлих налаштуваннях»).
- **Bitwig** офіційної світлої теми не має (тільки контраст і спільнотні
  моди) — не беремо за зразок.

### 3.2 Принципи

1. **Не чистий білий.** Полотно `#E8EAED` (не `#FFFFFF`): у студії з
   монітором на 300 кніт біле полотно сліпить, і тоді «білі» контроли вже
   нічим не виділити.
2. **Глибина — швом, не тоном.** У темній темі сходинка `BG→SURFACE` дає
   1,07:1, але око читає її разом із чорним швом. У світлій тональні сходинки
   фізично не можуть бути більшими за ~1,25:1, не виглядаючи брудно, тому
   `EDGE` стає несучим токеном: **2,2:1** до сусідів (і є «строгий» варіант
   `#8B9299` — 3,04:1, якщо хочемо формально закрити WCAG 1.4.11 для меж
   контролів).
3. **Один червоний.** Бренд лишається єдиним акцентом, але темнішим: на
   світлому `#F0584C` дає 2,8–3,4:1 (на `#E8EAED` — 2,81, на панелі — 3,21),
   цього мало і для тексту, і для тонких дуг.
4. **Адреси фарбують, дані не фарбуються темою.** Кольори треків/нот, які
   вибрав користувач (0xRRGGBB у проєкті), не перемикаються. Перемикаються
   лише «адресні» палітри за замовчуванням.
5. **Фейсплейти — це залізо.** Tide і Sampler лишаються темними в обох
   темах, як прилад на світлому столі. Але їхнє чорнило треба відв'язати від
   глобального (§3.6).

## 4. Системна тема

### 4.1 Факти (перевірено в коді, не з чуток)

| Факт | Джерело |
|---|---|
| `winit` на Linux **не знає** системної теми: `EventLoop::system_theme()` → `None` | `vendor/winit/src/platform_impl/linux/mod.rs:909-911` |
| X11-вікно: `theme()` → `None` | `vendor/winit/src/platform_impl/linux/x11/window.rs:1905` |
| `WindowEvent::ThemeChanged` на Linux не генерується (є лише в Windows/macOS) | немає жодної згадки в `vendor/winit/src/platform_impl/linux/` |
| `egui-winit` заповнює `system_theme` із winit при старті й на `ThemeChanged` | `egui-winit-0.31.1/src/lib.rs:158, :419` |
| `ThemePreference::System` без системної теми падає на `fallback_theme` (типово Dark) | `egui-0.31.1/src/memory/mod.rs:350-352` |
| Стандартний ключ: `org.freedesktop.appearance` / `color-scheme`, `u`: 0 = немає переваги, 1 = темна, 2 = світла; невідоме → 0 | специфікація порталу |
| Метод — `ReadOne` (v2); `Read` застарілий і повертає подвійний варіант | там само |

Висновок: **`ThemePreference::System` у egui на Linux не працює** — реалізація
«системної» теми — це наш запит до порталу, а не безкоштовна функція
фреймворку.

### 4.2 Визначення

Мінімальний шлях (без нових залежностей, у стилі `find_cjk_font()` із
`theme.rs:227`, який так само шелить до `fc-match`):

```rust
fn portal_color_scheme() -> Option<egui::Theme> {
    let out = std::process::Command::new("gdbus")
        .args(["call", "--session",
               "--dest", "org.freedesktop.portal.Desktop",
               "--object-path", "/org/freedesktop/portal/desktop",
               "--method", "org.freedesktop.portal.Settings.ReadOne",
               "org.freedesktop.appearance", "color-scheme"])
        .output().ok()?;
    let s = String::from_utf8(out.stdout).ok()?;
    // вивід: (<uint32 1>,)
    match s.split("uint32 ").nth(1)?.chars().next()? {
        '1' => Some(egui::Theme::Dark),
        '2' => Some(egui::Theme::Light),
        _   => None,                       // 0 = немає переваги
    }
}
```

Запитувати: на старті, при `Event::WindowFocused(true)` і не частіше ніж раз
на 30 с. Цього достатньо: користувач міняє тему в налаштуваннях системи,
повертається у вікно DAW — і дек перефарбовується. Підписка на
`SettingChanged` (через `zbus`) — «правильно», але для 0.2.0 це зайвий
асинхронний рантайм; `ashpd` + `pollster::block_on` (обидва вже в дереві) —
запасний варіант, якщо захочеться живої реакції.

Крайні випадки, які треба явно обробити:

- `gdbus`/`dbus-send` немає (мінімальний WM, контейнер) → `None` → відкат
  на `Dark` і чесний підпис у налаштуваннях: «система: невідомо (темна)».
- Портал є, але бекенд не реалізує `color-scheme` → помилка D-Bus → `None`.
- `XDG_CURRENT_DESKTOP` **не** використовувати як джерело істини: GNOME із
  увімкненою темною темою і GNOME зі світлою мають однаковий рядок.

### 4.3 Налаштування і пріоритет

```rust
// settings.rs, у GeneralSettings
#[derive(Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize)]
pub enum ThemeMode { #[default] Dark, Light, System }
pub theme: ThemeMode,   // #[serde(default)] уже стоїть на структурі
```

Пріоритет резолву:

1. `KFXL_THEME=dark|light|system` (env) — для скриншотів і живих перевірок
   (поруч із наявними `KFXL_CAPTURE_*`, `KFXL_X11`);
2. явний вибір у налаштуваннях (`Dark`/`Light`);
3. `System` → портал → `Dark`.

**Типове значення — `Dark`**, і це навмисно: оновлення не повинно
перефарбувати інтерфейс людині, яка цього не просила. «Системну» можна
запропонувати в Welcome на першому запуску (окремим рядком), але не
вмикати мовчки.

UI: Settings → General, картка «Вигляд» — `kit::chips` на три пункти
(`Темна / Світла / Системна`), під нею рядок стану: «система: світла
(портал)» або «система: невідомо → темна». Плюс `VIEW → Тема` (FL ставить
тему на F10, але F10 у нас уже MIDI-налаштування — тому в меню, без
хоткея, щоб не відбирати звичку).

### 4.4 Чого не робити

- Не читати `~/.config/gtk-3.0/settings.ini` чи `gsettings get
  org.gnome.desktop.interface color-scheme` напряму: це працює лише на
  GNOME і бреше на KDE/sway.
- Не ставити `ctx.set_theme(System)` і сподіватися, що egui сам усе
  зробить (§4.1).
- Не перемикати тему всередині кадру, у якому малюється дек: `apply()`
  міняє `Style`, а він читається на початку кадру — перемикання має
  відбуватися на початку `update()`, до панелей.

## 5. Тулбар

### 5.1 Блоки дека

Два ряди, `ROW1_H = 48`, `ROW2_H = 34` (`deck.rs:10-11`), `DECK_H = 82`
(`mod.rs:51`). Розкладка — `left_to_right`, метри — `right_to_left`
(`deck.rs:64`).

| # | id | Що | Ряд | Ширина ≈ | Ховати? |
|---|---|---|---:|---:|---|
| 1 | `transport` | Play / Stop / Record + таймер REC | 1 | 200 | **ні** (закріплено) |
| 2 | `mode` | чипси Pattern / Song | 1 | 170 | так |
| 3 | `lcd` | бар:крок, BPM, ▲▼, тактовий розмір | 1 | 272 | так (з попередженням) |
| 4 | `tap` | кнопка Tap tempo | 1 | 58 | так |
| 5 | `toggles` | Metronome / Count-in / Wait | 1 | 114 | так |
| 6 | `meters` | `cpu NN% voices NN` + лампа перевантажень | 1 | ~150 | так |
| 7 | `monitor` | осцилограф/спектр 110×32 | 1 | 116 | так (дублюється в VIEW) |
| 8 | `windows` | Playlist / Rack / Roll / Mixer / Browser | 2 | 5×~110 | так (є F5–F9, Alt+F8) |
| 9 | `snap` | дропдаун сітки | 2 | 110 | ні? (є в Piano Roll) |
| 10 | `pattern` | − / список / + | 2 | 222 | **ні** (щоденна робота) |
| 11 | `hint` | рядок підказки (решта ширини) | 2 | flex | так (перший кандидат) |

Ширини — оцінка з коду: клавіші 48/48/40 (`deck.rs:809,868`), LCD 272
(`:943`), кнопки вікон рахуються з тексту (`:141-147`), монітор 110 (`:484`),
`TOOL_H` 26 для другого ряду.

### 5.2 Модель

```rust
// settings.rs
#[derive(Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum DeckBlock {
    Transport, Mode, Lcd, Tap, Toggles, Meters, Monitor, // ряд 1
    Windows, Snap, Pattern, Hint,                        // ряд 2
}

#[derive(Clone, PartialEq, Serialize, Deserialize)]
#[serde(default)]
pub struct DeckSettings {
    pub row1: Vec<DeckBlock>,
    pub row2: Vec<DeckBlock>,
    pub hidden: Vec<DeckBlock>,
}
impl Default for DeckSettings { /* повний набір, порядок як у таблиці */ }

impl DeckSettings {
    /// Прибирає дублікати, повертає нові блоки на їхнє місце за
    /// замовчуванням, не дає сховати закріплені.
    pub fn normalise(&mut self) { /* … */ }
    pub fn visible(&self) -> impl Iterator<Item = DeckBlock> + '_ { /* … */ }
    pub fn height(&self) -> f32 {
        let r1 = if self.row1.is_empty() { 0.0 } else { ROW1_H };
        let r2 = if self.row2.is_empty() { 0.0 } else { ROW2_H };
        (r1 + r2).max(ROW1_H)          // порожній дек не має зникати цілком
    }
}
```

Ключові рішення:

- **`normalise()` обов'язковий.** `settings.ron` пише версія N, читає N+1:
  новий блок у 0.3.0 мусить з'явитися сам, а не зникнути назавжди, бо його
  немає в збереженому списку.
- **Порядок = порядок у `Vec`**, без окремих індексів: один масив на ряд,
  `hidden` — окремо. Це дає безкоштовно і приховування, і перестановку.
- **`DECK_H` стає функцією.** `TopBottomPanel::top("deck").exact_height(DECK_H)`
  (`mod.rs:3240-3241`) мусить брати `self.settings.general.deck.height()`,
  інакше прихований ряд 2 лишить 34 px порожнечі.
- **Закріплено лише `Transport`.** LCD ховати можна, але в UI він із
  підписом «без індикатора позиції» — це усвідомлений вибір, не недогляд.

### 5.3 UI

- **Settings → General → картка «Дек»**: два списки (Ряд 1 / Ряд 2), у
  кожному рядку — назва, `▲`/`▼` (не drag: кнопки фокусуються з клавіатури,
  drag — ні, а `ui-rules.md` вимагає повної клавіатурної навігації), і
  перемикач видимості; для `Transport` замість перемикача — `🔒`.
- Кнопки `Повний` / `Компактний` / `Скинути`. «Компактний» = прибрати
  `tap`, `windows`, `monitor`, `hint` — економія ~720 px по ширині
  (58 + 5×110 + 116) і 34 px по висоті.
- **Discoverability:** правий клік по порожньому місцю дека → «Налаштувати
  дек…» (відкриває ту саму сторінку) і `VIEW → Дек →` з тими самими
  перемикачами. Без цього про налаштування ніхто не дізнається.
- Усі рядки — через `i18n::Strings` (P1): нові ключі `deck_row1`,
  `deck_block_transport`, …, `theme_dark`, `theme_light`, `theme_system`.

### 5.4 Переповнення

Дек — одна горизонтальна лінія; при 1180 px (мінімум вікна) ряд 1 уже
~1080–1130 px плюс відступи `PAGE` 16×2 — тобто на межі. Два рівні захисту:

1. Перед малюванням блоку — `ui.available_width() >= block.min_width()`;
   якщо ні, блок не малюється (а не обрізається).
2. Пріоритет відсікання: `hint → tap → toggles → windows → meters →
   monitor`; `transport`, `pattern`, `snap` не відсікаються ніколи (їх
   відсутність зламає роботу).

Це ж правило робить вікно 1180 px придатним із увімкненими всіма блоками.

## 7. Ризики

| Ризик | Імовірність | Вплив | Що робити |
|---|---|---|---|
| `gamma_multiply` механічно замінити на `mix` — і зламати затемнення, де множення справді доречне (наприклад, тінь ноти вниз) | висока | середній | заміни лише там, де сенс «згаснути до фону»; градієнт ноти (`roll.rs:60`) лишити множенням |
| Фейсплейти: половина чорнила глобальна → у світлій темі Tide/Sampler стають нечитабельними | **дуже висока** | високий | P5.5 до першого релізу світлої теми; перевіряти скриншотом кожного приладу |
| Межі контролів не дотягують до 3:1 (WCAG 1.4.11) | середня | низький (текст проходить AA) | `EDGE #9AA1A9` як типовий, `#8B9299` як «строгий» варіант; рішення зафіксувати в `ui-rules.md` |
| Світла тема «пливе»: тональні сходинки ≤1,25:1 роблять панелі плоскими | висока | середній | глибина на `EDGE` + губа + `SHADOW` 24 %; перевіряти на скриншоті при 100 % і 150 % масштабу |
| `settings.ron` старої версії без нових полів | низька | низький | `#[serde(default)]` уже стоїть; додати тест «старий файл → дефолти» |
| Системна тема на X11/без порталу | середня | низький | відкат на `Dark`, підпис у налаштуваннях; `KFXL_THEME` для тестів |
| Перемикання теми під час вбудованого редактора плагіна (X11-дочірнє вікно) | середня | низький | вікно плагіна не перефарбовується — це нормально; не намагатися |
| Конфлікт із P1 (локалізація) | висока | низький | усі нові рядки одразу в `define_strings!` (EN+UK), тест паритетності ключів із P1 їх підхопить |
| Користувацькі кольори треків нечитабельні на світлому | середня | низький | `INK_ON_DARK/LIGHT` для написів; сам колір не чіпати |
| Дек: новий блок у наступній версії «зникає» у збереженому списку | середня | середній | `normalise()` + тест «старий DeckSettings без блоку → блок на місці» |
| Скриншоти в `docs/screenshots` застаріють | висока | низький | P5.9 разом із C5 (демо-проєкт) |

Окремо: **пастка «двох істин»**. Якщо палітра живе в `AtomicU8`, а
`Visuals` — у `Style`, їх треба міняти однією функцією `apply()`. Будь-яке
місце, що ставить `ctx.set_visuals(...)` напряму, розсинхронізує тему —
таких місць сьогодні немає, і це треба зберегти (додати коментар у
`theme.rs`).
