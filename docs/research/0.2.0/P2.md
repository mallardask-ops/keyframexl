# P2 — Іконка та логотип

Дослідження до завдання **P2** (`docs/v0.2.0.md:34-41`). Дата: 19.11.2026.
Обсяг: поточний стан, референси, вимоги Linux/GitHub, чотири концепти з SVG,
покроковий план виробництва і підключення.

**Коротко.** Поточна іконка — це 3×3 сітка падів у рамці; на 16 px вона
перетворюється на набір цяток із червоною точкою, а не на «K». Проблема не в
кольорі, а в масштабі деталей: рамка, колодязь, градієнти й скруглення 6/128
зникають на 16 px. Рекомендація — концепт **1 «Ступінь-K»**: той самий
кроковий пад, але K із трьох товстих штрихів, без рамки, з одним червоним
падом; шви між падами лишаються як деталь для 32–256 px і зникають на 16 px,
не руйнуючи форму. Плитка `#1A1B1D`, знак `#E9EAEB`, акцент `#F0584C`.
Додатково потрібні: `keyframexl.desktop`, дерево `hicolor` 16…512 +
`scalable`, PNG для `main.rs`, банер README і соціальне прев'ю 1280×640.

## 1. Поточний стан

### 1.1 Що намальовано

| Файл | Що це | Розмір |

| `assets/icon.svg` | іконка-знак | `viewBox 0 0 128 128`, 128×128 |
| `assets/icon.png` | растрова копія для вікна | 256×256, RGBA |

  завтовшки 2.
- «Колодязь»: `rect x=14 y=14 w=100 h=100 rx=18`, заливка `#0D0E10`,

- Сітка 3×3: пади `24×24`, `rx=6`, крок 28, координати 24/52/80.
  П'ять падів білі (градієнт `#F5F6F7 → #D6D8DC`): ліва колонка 3 шт.,

  Центральний — червоний (градієнт `#F76457 → #F0584C → #D63426`).
- Поверх червоного пада — біла смуга `14×2,6` (імітація velocity-бара).

`assets/logo.svg`:

- Той самий значок, вписаний у `translate(8 8) scale(0.4375)`, тобто 56×56.
- Словесна частина — живий `<text>`: `x=78 y=45`, IBM Plex Sans 600, 31 px,
  `letter-spacing -0,5`, «KeyFrame» кольору `#E9EAEB`; «XL» — `<tspan>`
  IBM Plex Mono 600, 22 px, `letter-spacing 1`, `dx=6`, колір `#F0584C`.

Інших брендових файлів немає: ні банера, ні соціального прев'ю, ні
`.desktop`, ні `hicolor`, ні 16/32/48 px.

### 1.3 Чому поточна іконка не працює на 16 px

Масштаб 128 → 16 — це 1/8. Перерахунок деталей:

| Деталь | У 128 | На 16 px | Наслідок |
| --- | --- | --- | --- |
| Обводка корпусу | 2 | 0,25 px | зникає |
| Обводка колодязя | 1,5 | 0,19 px | зникає |
| Пад | 24 | 3 px | стає цяткою |
| Зазор між падами | 4 | 0,5 px | зливається |
| Скруглення пада | 6 | 0,75 px | «з'їдає» квадрат |
| Velocity-бар | 2,6 | 0,32 px | невидимий |
| Поле до колодязя | 14 | 1,75 px | майже немає повітря |
| Рамка (корпус) | — | — | 39 % площі іконки |

Додатково:

1. **У сітці 3×3 немає діагоналей.** «K» існує лише за домовленістю: ліва
   колонка + центральний пад + два праві кути. На 16–32 px це читається як
   хрест або п'ять цяток, а не як літера (перевірено рендером `rsvg-convert`
   у 16/32/48/128 — на 16 px видно п'ять білих цяток, червону і темні
   провали).
2. **Градієнти на 3 px.** Вертикальний перехід `#F5F6F7 → #D6D8DC` на паді
   висотою 3 px — це один сірий піксель; замість «об'єму» виходить брудний
   край.
3. **Рамка забирає контраст.** Найяскравіше в іконці — білі пади, але 39 %
   площі займає майже чорний корпус, який на темній панелі просто зникає;
   на корисну площу припадає лише 61 %.
4. **Червоний пад не має ролі.** В інтерфейсі червоний = активний крок або
   hero-дія. В іконці він просто центр композиції; на 16 px це 3×3 px
   червона цятка без зв'язку з рештою.

### 1.4 Проблеми логотипу

- **Живий текст.** `logo.svg` не містить ані вбудованого шрифту, ані
  контурів. У браузері на GitHub текст відрендериться системним Sans, у
  `rsvg-convert` без встановленого IBM Plex — DejaVu; метрики й відступи
  «поплавуть». Для фіналу текст треба перевести в криві (Inkscape:
  *Path → Object to Path*) або вбудувати сабсет.
- **Змішаний регістр.** «KeyFrame» + «XL» — це не «моно-капс», який
  зафіксований у `docs/ui-rules.md:64`. Для пізнього TE і FL-канону
  природніше виглядає верхній регістр із трекінгом.
- **Значок у логотипі — 56 px.** Пади там 10,5 px, зазори 1,75 px: для
  56 px це на межі, а для 16 px-версії логотипу — непридатно. Логотип
  повинен мати окремий спрощений знак, а не масштабований 128-майстер.
- **Немає специфікації.** Не задані: охоронне поле, мінімальна ширина,
  монохромна версія, поведінка на світлому тлі, версія без словесної
  частини.

### 1.5 Чого немає в інфраструктурі

- `.desktop`-файлу немає взагалі (`grep -rn "desktop"` по репо дає лише
  `settings.rs` і workflow-и).
- Немає `share/icons/hicolor/*/apps/keyframexl.png`.
- Немає `scalable/apps/keyframexl.svg`.
- Немає 16/32/48 px — тільки 256 px PNG для вікна.
- Немає банера README, соціального прев'ю, аватара.
- Немає інсталятора і жодної перевірки, що іконки існують і квадратні.
- У tarball потрапляють лише бінарник, README і `docs/roadmap.md`
  (`release.yml:47-58`).

## 2. Референси: що виживає на 16–32 px

Метод: 19.11.2026 завантажено офіційні favicon/логотипи, відрендерено в
16/32/48 px і пораховано піксельні розміри деталей. Висновки — не «мені
здається», а те, що видно в растрі.

### 2.1 FL Studio — силует замість деталей

Знак — стилізований фрукт (помісь манго й полуниці; історія — на сайті
Image-Line [1]). У 16 px favicon це оранжево-червоне тіло з зеленим листком:
форма й листок читаються, внутрішні градієнти — ні. Урок: **один упізнаваний
силует + одна асиметрія** (листок) переживають будь-яке масштабування.
FL-конвенція, яку варто перенести: червоний = активний крок, а не декор.

Джерело: <https://www.image-line.com/fl-studio-news/fl-studio-fruit> [1].

### 2.2 Bitwig — груба матриця точок

Логотип — 3 ряди оранжевих кіл/квадратів (Wikimedia Commons [2]).
У favicon 16×16 це груба матриця квадратів ~2 px із зазором ~1 px: верхній
ряд коротший, середній довший, у нижньому є пропуск. Читається не як
«сітка», а як **патерн із пропуском**. Урок: крокова матриця може працювати
на 16 px, якщо:
- клітинка ≥ 2 px;
- зазор ≥ 1 px;
- патерн асиметричний (є «відсутній» пад);
- колір один, без градієнта.

Це прямий аргумент за «крокові пади» в іконці KeyFrameXL.

Джерело: <https://commons.wikimedia.org/wiki/File:Bitwig_Studio_Logo.svg> [2].

### 2.3 Ableton — чистий монохром і товсті смуги

Favicon 16×16 — це 4 вертикальні смуги ліворуч і 3 горизонтальні праворуч,
чорним по білому, товщина смуг 2 px, зазори 1–2 px, жодних кривих. Знак
читається ідеально, бо це **дві групи прямих** [3]. Урок: на 16 px криві й
діагоналі дорожчі за прямі; якщо форма вже має сенс, не варто додавати
об'єму.

Джерело: <https://www.ableton.com> (favicon 16×16) [3];
офіційні правила використання знаків —
<https://www.ableton.com/en/legal/branding-trademark-guidelines>.

### 2.4 REAPER — негативний приклад

Іконка — три напівпрозорі кола (синє, зелене, червоне) з білою дугою [4].
У 16 px вони змішуються в брудно-коричневу пляму: прозорість і накладання
кольорів на маленькому розмірі дають бруд. Урок: **не використовувати
напівпрозорість, множення кольорів і градієнти в іконці**. Для KeyFrameXL
це означає: шари тільки плоскі, один колір на шар.

Джерело: <https://www.reaper.fm> (favicon/logo) [4].

### 2.5 Renoise — бітмап-слово + одна плитка

Логотип: піксельний напис «renoise» малими літерами і мідно-оранжева похила
плитка з білою «R» [5]. На малому розмірі саме плитка стає іконкою, а
слово — ні.
Урок: **один знак + одна плитка**; піксельна типографіка доречна, якщо вона
не дрібніша за 2 px на штрих.

Джерело: <https://en.wikipedia.org/wiki/File:Renoise_logo.png> [5].

### 2.6 Teenage Engineering — світлий корпус, один акцент, моно-підписи

OP-1 field: алюмінієвий корпус, дисплей урівень із корпусом, «повністю
перероблена UI», новий шрифт, кольорові акценти на ручках [6]. OP-Z:
16 треків, мінімалістичний тактильний корпус [7]. Дизайн-аналітика TE
описує систему як «обмеження як естетика»: один акцентний колір,
чорний/білий, технічні моно-підписи, ніякого глянцю [8].

Що переносимо:
- плитка світла або темна, але **без градієнта**;
- рівно один акцент (у нас `BRAND #F0584C`);
- підписи — Plex Mono, верхній регістр, трекінг 0,12–0,18 em;
- «корпус» не малюємо: жодних гвинтиків, сіток, тіней.

Джерела: <https://teenage.engineering/products/op-1> [6],
<https://teenage.engineering/products/op-z> [7],
<https://blakecrosley.com/guides/design/teenage-engineering> [8].

### 2.7 Elektron — одна форма + один діагональний розріз

Favicon 32×32 — чорний квадрат, у якому біла геометрична «E» відрізана
діагоналлю [9]. Ніяких підписів, ніяких півтонів. Урок: **один розріз
створює впізнаваність**, а не кількість деталей. Це той самий прийом, що
діагональні «руки» K у концепті 1.

Джерело: <https://www.elektron.se> (favicon) [9],
<https://en.wikipedia.org/wiki/Elektron_(company)> [10].

### 2.8 Спільні правила для 16 px

| Правило | Число | Хто підтверджує |
| --- | --- | --- |
| Мінімальна товщина штриха | ≥ 2 px на 16 | Ableton, Bitwig, Elektron |
| Мінімальний зазор | ≥ 1 px на 16 | Bitwig, Ableton |
| Кількість форм у знаку | 1–3 | Elektron, Renoise, FL |
| Градієнти / прозорість | 0 | REAPER — антиприклад |
| Кольори | моно + 1 акцент | TE, Elektron, Bitwig |
| Асиметрія | 1 вісь або 1 пропуск | FL (листок), Bitwig (пропуск) |
| Перевірка | 16 px на темному і світлому тлі | Apple HIG, Microsoft [11][12] |

Apple HIG і Microsoft прямо радять спрощувати форму й уникати дрібних
деталей, які зникають у малому розмірі [11][12].

## 3. Вимоги платформи

### 3.1 freedesktop: тема іконок

Специфікація [13]:

- Іконки живуть у `$XDG_DATA_DIRS/icons/<theme>/<size>/<context>/` і
  `$XDG_DATA_HOME/icons/...`; для сторонніх програм — тема **`hicolor`**.
- Формати: PNG, SVG, XPM. PNG — рекомендований; **підтримка SVG
  опційна**. Порядок пошуку в теці: `png`, `svg`, `xpm`.
- Мінімум для застосунку — **48×48 PNG у `hicolor/48x48/apps`**; додатково
  можна `scalable/apps/*.svg`.
- Пошук: спочатку точний розмір, потім найближчий; якщо в поточній темі
  знайдено хоч якийсь розмір — пошук у спадкоємцях припиняється.
- Масштабні теки (`48x48@2`) — для HiDPI; для нас простіше дати 2×
  растри (32, 64, 128, 256, 512).

Рекомендований набір:

| Тека | Навіщо |
| --- | --- |
| `16x16/apps` | меню, трей, дрібні списки |
| `22x22/apps` | панелі XFCE/MATE |
| `24x24/apps` | панелі, список вікон |
| `32x32/apps` | доки, alt-tab |
| `48x48/apps` | **мінімум за специфікацією**, більшість меню |
| `64x64/apps` | KDE, HiDPI 32@2 |
| `128x128/apps` | доки, оглядач файлів |
| `256x256/apps` | сітка застосунків GNOME (типовий розмір) [14] |
| `512x512/apps` | HiDPI 256@2, великі прев'ю |
| `scalable/apps` | один SVG для всіх, хто його підтримує |

Ім'я файлу — **`keyframexl.png` / `keyframexl.svg`**, без розміру в імені.
`Icon=keyframexl` у `.desktop` — це ім'я для пошуку в темі, не шлях.

### 3.2 `.desktop`

Ключі, які нам потрібні [15]: `Type`, `Name`, `Exec`, `Icon`. `Icon` у
специфікації опційний, але без нього не буде іконки; значення — або
абсолютний шлях, або ім'я в темі. `StartupWMClass` — підказка для
групування вікна в X11-доку/лаунчері [15].

Пропонований файл `assets/share/applications/keyframexl.desktop`:

```ini
[Desktop Entry]
Type=Application
Version=1.5
Name=KeyFrameXL
GenericName=Music Production Studio
GenericName[uk]=Музична студія
Comment=Pattern-based music sequencer and DAW
Comment[uk]=Патерновий секвенсор і DAW
Exec=keyframexl %f
TryExec=keyframexl
Icon=keyframexl
Terminal=false
Categories=AudioVideo;Audio;Midi;Sequencer;
Keywords=DAW;sequencer;MIDI;music;beat;pattern;
Keywords[uk]=DAW;секвенсор;MIDI;музика;біт;патерн;
StartupNotify=true
StartupWMClass=keyframexl
```

- `Categories` — усі чотири категорії зареєстровані в меню-специфікації
  (`Midi`, `Sequencer` — додаткові категорії в `AudioVideo;Audio`) [16].
- `Exec=keyframexl %f` відкриває `.kfxl`/`.flp` як аргумент; `is_project_arg`
  у `src/main.rs:317-320` уже це приймає. Для повної асоціації файлів
  потрібен ще MIME-пакет (див. 5.3), інакше подвійний клік у файловому
  менеджері може не знати про `.kfxl`.
- `StartupWMClass=keyframexl` — див. 3.3.

### 3.3 Wayland, X11 і app_id

- Eframe/egui: `with_app_id` встановлює **Wayland application ID**. Дока
  каже: app_id має збігатися з іменем `.desktop`-файлу, «by using the
  application ID as file name» — це дає правильну іконку під Wayland [17].
  У нас `src/main.rs:281` уже має `"keyframexl"`, отже файл мусить бути
  **`keyframexl.desktop`** (Desktop File ID = ім'я файлу без `.desktop`)
  [18].
- Wayland: `xdg_toplevel.set_app_id` — саме те, що шукає композитор для
  зіставлення з `.desktop` [19].
- X11: `WM_CLASS` winit бере з `platform_specific.name`, а якщо його немає —
  з **імені бінарника** (`argv[0]`), тобто `keyframexl`
  (`vendor/winit/src/platform_impl/linux/x11/window.rs:386-400`). Тому
  `StartupWMClass=keyframexl` збігається. Якщо перейменувати бінарник
  (наприклад, `keyframexl-nightly`), групування зламається.
- **Критично:** `with_icon` на Wayland не працює — `Window::set_window_icon`
  має «Wayland: Unsupported» (`vendor/winit/src/window.rs:1200`). На
  Wayland іконку дає тільки `.desktop` + тема. На X11 `with_icon` ставить
  `_NET_WM_ICON`, але панелі все одно часто беруть іконку з `.desktop`.
  Отже `.desktop` і `hicolor` — не «бонус», а обов'язкова частина P2.

### 3.4 GitHub

  у Slack/Twitter/Telegram.

- «Favicon для GitHub» як такого не існує: репозиторій не має favicon.
  Є соціальне прев'ю і аватар. Якщо з'явиться сайт — окремо
  `favicon.ico` (16/32/48) + `icon-192.png`/`icon-512.png`.

### 3.5 README

## 4. Концепти

Спільна палітра для всіх чотирьох (тільки токени з `src/theme.rs`):

| Роль | Токен | HEX |
| --- | --- | --- |
| Плитка | `SURFACE` | `#1A1B1D` |
| Знак | `TEXT` | `#E9EAEB` |
| Акцент | `BRAND` | `#F0584C` |
| Тло навколо | `BG` | `#141516` |

Правила: `viewBox 0 0 256 256`, плитка `rx=56`, жодних градієнтів, тіней,
обводок і тексту; один червоний елемент; мінімальна товщина — 36–48
одиниць (2,25–3 px на 16). Плитка — частина іконки; у самому інтерфейсі
(`icon_brand`) знак малюється **без плитки**, бо поверхня вже є.

На темній панелі плитка `#1A1B1D` майже зливається з тлом — і це нормально:
знак читається як білий K (як у Ableton). На світлому тлі плитка працює як
бейдж і дає контраст. Саме тому потрібні обидві перевірки з 5.6.

Світла версія плитки (`#E9EAEB` + знак `#141516` + пад `BRAND`) — не
основна, але корисна для друку, світлих доків і як «паперовий» варіант у
стилі OP-1; вона є в 4.1 як альтернатива.

### 4.1 Концепт 1 — «Ступінь-K»

**Ідея.** Еволюція поточної іконки, але K зібраний не з сітки 3×3, а з
трьох товстих штрихів: вертикальна стійка з трьох падів і дві діагональні
«руки». Між падами — шви 8 одиниць; на 32–256 px вони читаються як
сегментний LCD, на 16 px зливаються, і лишається чистий K. Середній пад
стійки — червоний: це «активний крок», як у FL.

**Чому читається на 16 px.** Стійка — 3 px, руки — 2,75 px, зазор між
падами — 0,5 px (тобто зникає, а не додає шуму). Силует — літера K, яку
неможливо сплутати з сіткою. Червоний пад — 3×3,5 px, єдина кольорова
цятка. Це та сама логіка, що у favicon Bitwig: груба матриця + асиметрія,
але тут асиметрія — діагоналі.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 256 256" width="256" height="256">
  <rect width="256" height="256" rx="56" fill="#1A1B1D"/>
  <g fill="#E9EAEB">
    <rect x="44" y="36" width="48" height="56" rx="4"/>
    <rect x="44" y="164" width="48" height="56" rx="4"/>
    <rect x="88" y="106" width="136" height="44" rx="4" transform="rotate(-45 88 128)"/>
    <rect x="88" y="106" width="136" height="44" rx="4" transform="rotate(45 88 128)"/>
  </g>
  <rect x="44" y="100" width="48" height="56" rx="4" fill="#F0584C"/>
  <g fill="#1A1B1D">
    <rect x="132.1" y="52" width="8" height="56" transform="rotate(-45 136.1 80)"/>
    <rect x="132.1" y="148.1" width="8" height="56" transform="rotate(45 136.1 176.1)"/>
  </g>
</svg>
```

Примітки:

- Шви малюються кольором плитки, тому іконка не призначена для прозорого
  тла без плитки. Для прозорого варіанта (favicon сайту) шви прибрати.
- Для 16 px існує окремий оптичний майстер (див. 5.2): там стійка суцільна,
  а шви відсутні.
- У `icon_brand` малюється та сама форма K, але суцільна, без швів і без
  плитки.
- Світла версія (для друку/світлих доків): плитка `#E9EAEB`, знак
  `#141516`, пад `BRAND`; геометрія без змін.

### 4.2 Концепт 2 — «Кадр»

**Ідея.** Знак — ромб ключового кадру (keyframe), порожній усередині, з
червоним ромбом-ядром. Це найабстрактніший і найбільш «інструментальний»
варіант: він не показує літеру, а показує об'єкт, з яким працює програма —
кадр на таймлайні. Форма симетрична, тому добре центрується в будь-якому
макеті і добре працює як аватар.

**Чому читається на 16 px.** Один силует 13×13 px, товщина кільця 3,5 px,
отвору — 6 px, червоне ядро — 3 px. Немає жодної лінії, тоншої за 3 px;
немає кутів, які треба «домальовувати» очима. Це прийом Elektron: одна
форма + один внутрішній розріз.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 256 256" width="256" height="256">
  <rect width="256" height="256" rx="56" fill="#1A1B1D"/>
  <path d="M128 24 L232 128 L128 232 L24 128 Z" fill="#E9EAEB"/>
  <path d="M128 80 L176 128 L128 176 L80 128 Z" fill="#1A1B1D"/>
  <path d="M128 104 L152 128 L128 152 L104 128 Z" fill="#F0584C"/>
</svg>
```

Ризик: ромб — поширений мотив у відеоредакторах і картах; без контексту
може читатися як «rotate» або «play». Тому його добре підтримує слово
«KEYFRAME» у логотипі.

### 4.3 Концепт 3 — «Сходи»

**Ідея.** Три горизонтальні смуги різної довжини, вирівняні по лівому краю,
як кроки секвенсора або velocity-профіль. Верхня — червона. Це найбільш
«функціональний» знак: він каже «послідовність кроків», а не «літера K».

**Чому читається на 16 px.** Три смуги по 2,75 px, зазори 1,5 px, довжини
11,5 / 7,75 / 4 px. Око бачить три рівні й один червоний — цього достатньо.
Але це найслабший варіант на 16 px: без контексту він читається як список
або діаграма, а не як музичний інструмент. Тому його варто розглядати як
«другий знак» для документації, а не як головну іконку.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 256 256" width="256" height="256">
  <rect width="256" height="256" rx="56" fill="#1A1B1D"/>
  <rect x="36" y="180" width="184" height="44" rx="4" fill="#E9EAEB"/>
  <rect x="36" y="112" width="124" height="44" rx="4" fill="#E9EAEB"/>
  <rect x="36" y="44" width="64" height="44" rx="4" fill="#F0584C"/>
</svg>
```

### 4.4 Концепт 4 — «Енкодер»

**Ідея.** Кільце енкодера TE з прорізом на 12 годині й червоним ковпачком
всередині. Це прямий відсил до ручок OP-1/OP-Z і до `kit::knob`; знак
говорить «крутилка/синтез», а не «нота». Найкраще працює в парі з
моно-підписом.

**Чому читається на 16 px.** Зовнішній діаметр 13,75 px, товщина кільця
2,25 px, червоний центр 5,5 px. Проріз 1,5 px на 16 px майже зникає, і
знак стає «пончиком» із червоною точкою — теж читабельно. Це єдиний
концепт, який не є літерою, але й не ромбом; він найкраще диференціює
бренд від «ще однієї DAW».

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 256 256" width="256" height="256">
  <rect width="256" height="256" rx="56" fill="#1A1B1D"/>
  <circle cx="128" cy="128" r="92" fill="none" stroke="#E9EAEB" stroke-width="36"/>
  <rect x="116" y="14" width="24" height="48" fill="#1A1B1D"/>
  <circle cx="128" cy="128" r="44" fill="#F0584C"/>
</svg>
```

Ризик: на 32–48 px без прорізу кільце читається як вініл або кнопка
живлення. Проріз треба робити ширшим (32 одиниці), якщо тест на 24 px
покаже «запис».

### 4.5 Порівняння

Оцінки — суб'єктивні, але спираються на рендери 16/32/48/256, а не на
«відчуття»: 5 = форма впізнається без контексту, 3 = потрібен підпис.

| | 16 px | 32 px | 256 px | Унікальність | Зв'язок із брендом | Головний ризик |
| --- | --- | --- | --- | --- | --- | --- |
| 1. Ступінь-K | 5/5 | 5/5 | 4/5 | 4/5 | 5/5 (K + пад) | шви на 24–32 px можуть виглядати брудно |
| 2. Кадр | 5/5 | 5/5 | 4/5 | 3/5 | 4/5 (keyframe) | «play/rotate» без підпису |
| 3. Сходи | 3/5 | 4/5 | 4/5 | 4/5 | 3/5 (секвенсор) | читається як список/діаграма |
| 4. Енкодер | 4/5 | 5/5 | 4/5 | 4/5 | 4/5 (TE-ручка) | вініл/живлення на середніх розмірах |

**Рекомендація:** концепт **1** як основна іконка і знак у програмі.
Концепт **2** — резервний варіант: якщо на реальних панелях K виявиться
занадто «літерним», він замінює 1 **всюди**, а не співіснує з ним.
Концепти 3 і 4 лишити як напрями для
документації/обкладинок, не як головну іконку.

Чому 1, а не 2: у продукту вже є назва «KeyFrameXL» і внутрішня назва знака
«Step Matrix K» (`docs/ui-rules.md:150`). K з падів зберігає обидві
ідентичності й водночас виправляє головну ваду — сітку без діагоналей.
Концепт 1 також єдиний, який природно несе «кроковий пад» і «сегментний
LCD» одночасно.

### 4.6 Логотип (словесна частина)

Логотип = знак + слово. Пропорції:

- Висота знака `H`; слово — верхній регістр.
- «KEYFRAME» — IBM Plex Sans **600**, `font-size ≈ 0.52H`, трекінг
  `+0.04em` (не більше: інакше слово розсипається).
- «XL» — IBM Plex Mono **500**, той самий кегль, колір `BRAND #F0584C`,
  трекінг `+0.14em`, відступ від слова `0.12em`.
- Базова лінія — на `0.69H` від верху знака; оптичне центрування, не
  математичне.
- Охоронне поле — `0.5H` з усіх боків; мінімальна ширина логотипа —
  240 px (нижче — тільки знак).
- Основна версія: знак `TEXT`, пад і «XL» — `BRAND`.
- Монохромна версія (друк, вишивка, один колір): усе `#141516` на світлому
  або `#E9EAEB` на темному, без `BRAND`.
- **Текст у фінальному SVG — криві.** Не покладатися на `font-family`.

Червоний у логотипі з'являється двічі — пад у знаку й «XL» — але це **один
акцентний колір** у двох масштабах; в іконці він один. Не додавати третій
червоний (смугу, підкреслення, точку).

Ескіз (не фінал; текст треба перевести в криві):

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 1400 256" width="1400" height="256">
  <rect width="256" height="256" rx="56" fill="#1A1B1D"/>
  <g fill="#E9EAEB">
    <rect x="44" y="36" width="48" height="56" rx="4"/>
    <rect x="44" y="164" width="48" height="56" rx="4"/>
    <rect x="88" y="106" width="136" height="44" rx="4" transform="rotate(-45 88 128)"/>
    <rect x="88" y="106" width="136" height="44" rx="4" transform="rotate(45 88 128)"/>
  </g>
  <rect x="44" y="100" width="48" height="56" rx="4" fill="#F0584C"/>
  <!-- ескіз: у фіналі цей текст має бути контурами -->
  <text x="320" y="176" font-family="IBM Plex Sans" font-size="132" font-weight="600"
        letter-spacing="5" fill="#E9EAEB">KEYFRAME</text>
  <text x="1120" y="176" font-family="IBM Plex Mono" font-size="132" font-weight="500"
        letter-spacing="18" fill="#F0584C">XL</text>

```

Технічний варіант для статус-бару/About: увесь напис `KEYFRAMEXL` у Plex
Mono 500, великими літерами, трекінг `0.18em`, без червоного (колір
успадковується від теми). Це відповідає правилу «моно-капс» і не конкурує з
hero-кнопкою.

### 5.2 Рендер SVG → PNG

`rsvg-convert` (є в системі, libRSVG):

```sh
set -eu
master=assets/brand/icon.svg
small=assets/brand/icon-16.svg
out=assets/share/icons/hicolor

mkdir -p "$out"/{16x16,22x22,24x24,32x32,48x48,64x64,128x128,256x256,512x512}/apps
mkdir -p "$out/scalable/apps"

# 16 px — тільки з оптичного 16-майстра, не з 256!
rsvg-convert -w 16  -h 16  "$small"  -o "$out/16x16/apps/keyframexl.png"
# 22–512 — з 256-майстра
for s in 22 24 32 48 64 128 256 512; do
  rsvg-convert -w "$s" -h "$s" "$master" -o "$out/${s}x${s}/apps/keyframexl.png"
done

# віконна іконка для include_bytes! (main.rs:325)
rsvg-convert -w 256 -h 256 "$master" -o assets/icon.png

# scalable
cp "$master" "$out/scalable/apps/keyframexl.svg"

# перевірка
identify "$out"/*/apps/keyframexl.png | awk '{print $1, $3}'
```

`resvg` (швидший, краще з антиаліасингом; ставиться окремо):

```sh
resvg --width 256 --height 256 assets/brand/icon.svg \
      assets/share/icons/hicolor/256x256/apps/keyframexl.png
resvg --width 16  --height 16  assets/brand/icon-16.svg \
      assets/share/icons/hicolor/16x16/apps/keyframexl.png
```

Правила рендеру:

- Не масштабувати 256 → 16 напряму: на 16 px потрібен окремий майстер із
  піксельними пропорціями (3 px стійка, 3 px руки), а не зменшений 256.
- Не використовувати `-b` (фон): кути плитки мають бути прозорими.
- Перевіряти, що всі PNG квадратні, RGBA, без інтерлінгу:
  `identify -format '%f %wx%h %[channels]\n'`.
- Оптимізація (опційно): `oxipng -o4 --strip safe`.

16-майстер для концепту 1 (піксельні пропорції, без швів):

```svg
  <rect x="5.5" y="6.4" width="8.5" height="3.2" transform="rotate(45 5.5 8)" fill="#E9EAEB"/>
  <rect x="3" y="2" width="3" height="12" fill="#E9EAEB"/>
  <rect x="3" y="6" width="3" height="4" fill="#F0584C"/>
</svg>
```

### 5.3 Інсталятор і `.desktop`

`scripts/install.sh` (ставить у `$PREFIX`, типово `~/.local`):

```sh
#!/bin/sh
set -eu
PREFIX="${PREFIX:-$HOME/.local}"
HERE=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)

# tarball: $HERE/share; репо: $HERE/../assets/share
DATA="$HERE/share"
[ -d "$DATA" ] || DATA="$HERE/../assets/share"

BIN="${1:-$HERE/keyframexl}"
[ -x "$BIN" ] || BIN="$HERE/../target/release/keyframexl"

install -Dm755 "$BIN" "$PREFIX/bin/keyframexl"
install -Dm644 "$DATA/applications/keyframexl.desktop" \
  "$PREFIX/share/applications/keyframexl.desktop"

for s in 16 22 24 32 48 64 128 256 512; do
  install -Dm644 "$DATA/icons/hicolor/${s}x${s}/apps/keyframexl.png" \
    "$PREFIX/share/icons/hicolor/${s}x${s}/apps/keyframexl.png"
done
install -Dm644 "$DATA/icons/hicolor/scalable/apps/keyframexl.svg" \
  "$PREFIX/share/icons/hicolor/scalable/apps/keyframexl.svg"

command -v gtk-update-icon-cache >/dev/null &&
  gtk-update-icon-cache -f -t "$PREFIX/share/icons/hicolor" || true
command -v update-desktop-database >/dev/null &&
  update-desktop-database "$PREFIX/share/applications" || true
```

Перевірити, що `$PREFIX/bin` є в `PATH` (інакше `TryExec` у `.desktop`
сховає запис із меню): для `~/.local` це `~/.local/bin`.

Опційно — MIME для `.kfxl`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<mime-info xmlns="http://www.freedesktop.org/standards/shared-mime-info">
  <mime-type type="application/x-keyframexl">
    <comment>KeyFrameXL project</comment>

    <glob pattern="*.kfxl"/>
  </mime-type>
</mime-info>
```

`install.sh` — `install -Dm644 "$DATA/mime/packages/keyframexl.xml"
$PREFIX/share/mime/packages/keyframexl.xml` + `update-mime-database`.

Приклад патчу для `kit.rs` (скелет, не фінальний код):

```rust
fn rot_quad(r: Rect, center: Pos2, deg: f32) -> Vec<Pos2> {
    let (sin, cos) = deg.to_radians().sin_cos();
    let f = |p: Pos2| {
        let d = p - center;
        center + vec2(d.x * cos - d.y * sin, d.x * sin + d.y * cos)
    };
    vec![
        f(r.left_top()),
        f(r.right_top()),
        f(r.right_bottom()),
        f(r.left_bottom()),
    ]
}

pub fn icon_brand(p: &Painter, rect: Rect) {
    let s = rect.width().min(rect.height());
    let base = Rect::from_center_size(rect.center(), vec2(s, s));
    let u = s / 256.0;
    let box_at = |x: f32, y: f32, w: f32, h: f32| {
        Rect::from_min_size(base.min + vec2(x * u, y * u), vec2(w * u, h * u))
    };

    if s <= 22.0 {
        // 16 px optical: стійка 3×12, червоний пад 3×4,
        // руки — дві `Shape::convex_polygon` з 4 точок (див. icon-16.svg).
        let u16 = s / 16.0;
        let b16 = |x: f32, y: f32, w: f32, h: f32| {
            Rect::from_min_size(base.min + vec2(x * u16, y * u16), vec2(w * u16, h * u16))
        };
        p.rect_filled(b16(3.0, 2.0, 3.0, 12.0), CornerRadius::ZERO, t::TEXT);
        p.rect_filled(b16(3.0, 6.0, 3.0, 4.0), CornerRadius::ZERO, t::BRAND);
        return;
    }

    // Без плитки й без швів: руки, стійка, червоний пад.
    p.add(Shape::convex_polygon(
        rot_quad(box_at(88.0, 106.0, 136.0, 44.0), base.min + vec2(88.0, 128.0) * u, -45.0),
        t::TEXT,
        Stroke::NONE,
    ));
    // ... друга рука (+45°), стійка, червоний пад
}
```

Важливо: у `egui::Painter` немає готового `rotate` для `rect_filled`, тому
руки малюються як `Shape::convex_polygon` із чотирьох повернутих точок.
`rot_quad` вище — робочий helper. Для 16 px поворот можна не робити: руки
з 5.2 задані повернутими прямокутниками, але їх можна замінити двома
полігонами з тими самими вершинами.

### 5.6 QA

1. **16 px на очах.** Відкрити PNG 16×16 у файловому менеджері при 100 %
   (не збільшувати) на темній і світлій панелі. Якщо K не читається — не
   «домальовувати», а міняти майстер.
2. **Контактний аркуш** 16/22/24/32/48/64/128/256 на `#141516` і `#E9EAEB`.
3. **Вікно X11:** `xdotool search --name KeyFrameXL | head -1` →
   `xprop -id <id> WM_CLASS` має дати
   `WM_CLASS(STRING) = "keyframexl", "keyframexl"`; `xprop -id <id>
   _NET_WM_ICON` не порожній.
4. **Wayland:** `WAYLAND_DEBUG=1 ./target/release/keyframexl 2>&1 | grep -m1
   set_app_id` → `set_app_id("keyframexl")`; іконка в докі/огляді вікон.
5. **Меню/About/Welcome:** знак не «губить» червоний пад на 16/40/48.
6. **README:** банер не розтягується, текст не дрібніший за 18 px на 1×;
   social preview відкривається у 1280×640 і < 1 MB.
7. **Логотип:** відкрити `logo.svg` з вимкненим IBM Plex (або в
   `rsvg-convert` без шрифту) — текст не має «плисти», бо він кривий.
8. **Регрес:** `cargo build --release` після заміни `icon.png`; перевірити,
   що `include_bytes!` не зламався і бінарник не виріс різко.
