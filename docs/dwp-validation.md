# DirectWave (`.dwp`) Import & Validation

KeyFrameXL's built-in **Sampler** supports importing DirectWave `.dwp` presets by converting them through **ConvertWithMoss** (20.2.0+) into normalized SFZ + WAV data and embedding all audio and zone parameters directly inside the `.kfxl` project file.

Once imported, a project is completely self-contained and portable — playback and reopening do not require ConvertWithMoss or the original `.dwp` file.

Reference: [ConvertWithMoss 20.2.0 release](https://github.com/git-moss/ConvertWithMoss/releases/tag/20.2.0)

---

## Design & Validation Principles

1. **Preserve originals without redistribution:** Keep original `.dwp` bytes and source metadata separate; never bundle private or copyrighted presets in the repository.
2. **Test real musical boundaries:** Exercise notes just inside and outside key and velocity boundaries, repeated attacks, chords, sustained loops, and release tails against known sample rates and tempos.
3. **Treat converter output as an observation, not ground truth:** Record the exact ConvertWithMoss version, license, artifact size, and command. Because ConvertWithMoss normalizes through SFZ, some DirectWave fields are approximated or omitted.
4. **Track parameter fidelity explicitly:** Record every parameter as reproduced, approximated, omitted, or unverified; surface unsupported SFZ opcodes in the in-app import report rather than silently dropping them.
5. **Test storage formats independently:** Validate FLAC monoliths, legacy PCM monoliths, external WAV folders, stereo preservation, missing-file relinking, and relocated portable projects separately. Use frame-accurate impulse markers to verify loop boundaries.
6. **Decouple importer, resolver, and voice engine:** Store normalized instrument data, decoded samples, original source bytes, and the import report in the project so playback never depends on external tools.

## Single-Zone Synthetic Test (2026-11-14)

- **Fixture:** `tests/fixtures/dwp` — a 48 kHz, 16-bit mono C4 sine wave (24,000 frames), mapped in SFZ across keys `48–72` with root `60`.
- **Converter:** ConvertWithMoss 20.3.0 (upstream LGPL-3.0, 52,701,888-byte Ubuntu package with bundled Java runtime; not redistributed in this repo).
- **Round-trip (`SFZ → monolithic DWP → SFZ/WAV`):**
  - Recovered root and key range matched exactly (`60` / `48–72`).
  - Recovered WAV matched the source PCM bytes from the start, with 24,064 total frames (a 64-frame padding difference at the tail is recorded rather than treated as an exact length match).
  - Exercised through KeyFrameXL's importer via `KEYFRAMEXL_CONVERTER`. (Early importer limits from this first pass — mono downmix, single-zone only, no loops/envelopes/filters — were later superseded by Sampler v2.)

## Multi-Zone Validation Test (2026-11-14)

- **Fixture:** `tests/fixtures/multizone/source/Zones.sfz` — four original CC0 stereo WAVs (4,800 frames each at 48 kHz), generated by `scripts/make_dwp_fixture.py`.
- **Signals:** Periodic 125 Hz and 250 Hz reference tones (pure sine for the soft layer; sine + 3rd harmonic for the loud layer), deliberately designed as frame-aligned control signals rather than concert-tuned presets so loop boundaries can be verified down to the exact sample.

| Zone | Key Range | Velocity | Root | Attack / Decay / Sustain / Release |
| --- | --- | --- | --- | --- |
| Low soft | `48–59` | `1–63` | `48` | `0.08 s` / `0.12 s` / `60%` / `0.22 s` |
| Low bright | `48–59` | `64–127` | `48` | `0.005 s` / `0.07 s` / `80%` / `0.40 s` |
| High soft | `60–72` | `1–63` | `60` | `0.20 s` / `0.15 s` / `40%` / `0.25 s` |
| High bright | `60–72` | `64–127` | `60` | `0.002 s` / `0.15 s` / `70%` / `0.60 s` |

### Verified Behavior
- **Loop boundaries:** All four loops span source frames `[384, 4224)` (converted from SFZ's inclusive `loop_end=4223`). ConvertWithMoss 20.3.0 preserves loop points and the first 4,800 stereo frames exactly, padding each recovered WAV to 5,120 frames outside the loop region.
- **Opcode inheritance & envelopes:** Inherited `<global>` and `<group>` SFZ opcodes expand into every region. ADSR parameters agree within `1 µs` / `0.000001` sustain fraction. (KeyFrameXL currently uses linear ADSR curves as an approximation of DirectWave's curves.)
- **Automated acceptance suite:** Verifies key split boundaries (`59`/`60`), velocity split boundaries (`63`/`64`), silence outside valid ranges and at velocity `0`, stereo PCM preservation, continuous forward looping past sample end, soft attack ramp vs. instantaneous control, and release decay to silence. Forward, sustain, and ping-pong loop boundaries also have independent frame-level unit tests.
- **Portability check:** After importing, the source `.dwp` is deleted, the `.kfxl` project is saved, moved to a different directory, and the original copy is removed. Reopening restores all embedded samples and parameters without calling ConvertWithMoss, and the rendered WAV matches the original render **byte for byte**.
- **Saved artifact:** `artifacts/dwp-multizone/Zones.kfxl` (4 two-second bars playing keys `48, 48, 60, 60` at velocities `40, 110, 40, 110`, plus release tail) and `artifacts/dwp-multizone/report.txt`.

### Reproducing Locally

Point `KEYFRAMEXL_CONVERTER` to your local ConvertWithMoss executable and run:

```sh
python3 scripts/make_dwp_fixture.py --converter "$KEYFRAMEXL_CONVERTER"
KEYFRAMEXL_ARTIFACTS=artifacts/dwp-multizone cargo test multizone_ranges_loops_adsr_and_disk_roundtrip
```

## Unverified Areas & Current Scope

- **Not yet validated against DirectWave directly:** No reference audio renders from Image-Line DirectWave have been compared side by side.
- **Unverified variants in this pass:** Legacy PCM monoliths, external-WAV `.dwp` programs, exact envelope curvature, and DirectWave per-voice FX.
- **Explicit rejections:** Unsupported modes (such as one-shot gates and sustain ping-pong loops) are reported and rejected rather than silently altered.
- **Migration:** Earlier single-zone `.kfxl` project documents are automatically migrated on load.
- **Future native reader:** Because ConvertWithMoss omits some DirectWave blocks (e.g. `ENV 1/2`, the second filter, and most modulation matrix slots), full fidelity will eventually require a native `.dwp` binary reader.
