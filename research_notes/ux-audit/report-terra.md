# KeyFrameXL UX research audit

15 November 2026. Research only; no source changes. Severity is about interruption to music-making, not aesthetic preference. Estimates are engineering days for one developer, excluding plugin-host edge cases.

## 1. Method and limits

I opened all 25 supplied PNGs as five contact sheets at their native 1366-pixel width (the two 1920 images were reduced to fit); file names below resolve under [screens](screens/). I read the design rules and inspected the relevant source, particularly `mod.rs::shortcuts`, `menu.rs`, `kit.rs`, `rack.rs`, `files.rs`, and `workspace.rs`. This is a static review, not a live interaction or accessibility test: screenshots show states, not event ordering, capture, latency, actual focus, platform DPI, or persistence. Recommendations are marked as such; absence of a visible control is not proof that a feature is absent. I did not read report-muse.md. No FL installation was operated. Official manuals below contain labeled screenshots and are the visual reference; no third-party image is represented as our own screenshot.

## 2. Area audit and proposed interaction contract

Measurements below are starting design targets in egui **points** at 100% and approximately pixels at 1x, not purported measurements of FL. Keep the OS pixels-per-point factor and multiply by user zoom; test 100%, 125%, 150%, 200%, fractional scaling and moving monitors. Make the shell usable at 1366×768 without a clipped primary action, and preserve scrolling/reflow at 900×620.

### Shell, workspace and scale

**Evidence:** [01](screens/01-main-arrange.png), [02](screens/02-compose-roll.png), [03](screens/03-edit-workspace.png), [07](screens/07-floating-roll.png), [24](screens/24-main-1920.png), [25](screens/25-roll-1920.png); `workspace.rs::preset_layout`, `win`, `dock_style`; `mod.rs::new`; `menu.rs::menu_view`. There is already `egui_dock` and saved workspace/zoom. The forced 1.0 pixels-per-point is guarded by screenshot capture mode, not normal startup. FL's [desktop overview](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/boxinstaller/WebContent/FLStudio20_GettingStartedManual.pdf) shows switchable, resizable windows.

**Problem:** Each editor pays for a dock title, then another 55–60-point header and framed inset. 02 gives the piano roll only a narrow vertical band; 03 clips the rack. At 1920, rack controls remain clustered in a sea of empty panel. Tiny captions and miniature knobs coexist with oversized framing. A hidden action hint is truncated at the top. The predefined workspace switcher also occupies asset-browser space.

**Fix:** title/tab strip 26–30, editor toolbar 30–34, footer 22–24; resize splits with visible 5–7-point grab zones, sensible minima (rack 180 high, roll 260 high, playlist 200 high) and no fixed blank padding. Collapse browser to 0; default 220, resize 180–360. When height is insufficient favor the focused editor, let others tab or scroll. Active tab gets a visible focus treatment; right-click tab Float/Dock/Close; drag with a preview and Escape to cancel. Keep `egui_dock`, use its tab context menu rather than a second window manager. Persist layout per workspace; recover offscreen floating windows on display change. Verify zoom menu shortcuts rather than trusting their labels: `menu_view` advertises Ctrl++/−/0, while `shortcuts()` does not implement those explicitly; egui's own handling must be tested before calling this broken.

### Transport

**Evidence:** 01–05, `deck.rs`, `mod.rs::play_pause`, `stop`, `shortcuts`. FL documents Space play/stop, Ctrl+Space pause, and L PAT/SONG, along with transport and record modes in its [toolbar manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/toolbar_panels.htm).

**Problem:** Play is the strongest red object even when the adjacent record button communicates arming; the seven-segment readout is decorative at the expense of legibility. Separate Tempo knob and display duplicate information. Small window icons have no enduring text labels.

**Fix:** group 34×34 transport buttons, a 56–72-point PAT/SONG toggle, and editable 64–72-point BPM; record armed state must remain distinct from playback. Single click toggles transport; double click numeric value edits; Enter commits, Escape cancels, wheel adjusts only while hovered and focused, Shift for fine adjustment. Show position in legible tabular figures. Status hints identify hovered control and shortcut. Use standard `Button`, `DragValue`, `ComboBox`, with custom painting restricted to transport faces and meters.

### Main menus and dialogs

**Evidence:** [08](screens/08-menu-file.png), [09](screens/09-menu-add.png), [10](screens/10-menu-options.png), [11](screens/11-menu-view.png), [16–18](screens/16-settings-audio.png), [22](screens/22-shortcuts.png), [23](screens/23-export-dialog.png); `menu.rs::main_menu`, `menu_file` through `menu_help`, `settings_ui.rs`, `export.rs::export_window`. The main menu already uses `ui.menu_button`, not a completely bespoke popup. `item` imposes 240×26 minimum; the resultant menus in 08–11 look disproportionately tall against the tiny content. In screenshot 22 the shortcut list extends beyond the viewport; that is a concrete reachability problem in the baseline.

**Fix:** menu rows 26–28 high, width 210–280 based on content, 13–14 text, high-contrast accelerator column, visible checked/disabled state. Keep standard menu behavior and test keyboard arrows, submenu direction, click outside and Escape on the actual egui version. File: New/Open/recent/Save/Save as/Export/Import/Exit; Edit: actual undo/redo and context-sensitive Cut/Copy/Paste, disabled with reason when not supported; Add: generators and effect picker, not an action misleadingly called Effect that merely opens Mixer; Patterns: new, clone, rename, delete; View: checked window toggles and workspace; Options: settings and enabled toggles; Tools: real actions; Help: help and searchable shortcuts. `Ctrl+Shift+Ins` is printed for Add Pattern but is not present in global `shortcuts()`; audit other context handlers before asserting it is unimplemented globally.

Use `egui::Window` for nonmodal settings and plugin editors; use the egui 0.31 modal facility where supported, or an input-blocking foreground layer for decisions and export. Center/clamp to the visible viewport; max height viewport minus 32 with a `ScrollArea`, and fixed action footer. Escape cancels the active dialog, Enter activates the default only when text input/IME or a focused button has not consumed it; restore focus to invoker. Export currently explicitly checks Enter and Escape in `export_window`; test whether Enter in a field accidentally launches export and whether modal input leaks. Settings should expose sample rate, buffer and actual latency with clear apply/failure state; MIDI shows device state and panic; plugin scan failure names the affected plugin and next action. Preserve unsaved work when close is requested.

### Context menus and gestures

**Evidence:** [12](screens/12-rclick-channel.png), [13](screens/13-rclick-step.png), [15](screens/15-mixer-slot-picker.png); `rack.rs::channel_label`, `toggle_step`, `channel_strip`, `workspace.rs::context_menu`, `files.rs::files_tab`, `roll.rs`, `playlist.rs`, `mixer.rs`. FL's [piano roll](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm), [playlist](https://cluster.image-line.com/fl-studio-learning/fl-studio-online-manual/html/playlist.htm), and [mixer](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/mixer.htm) describe different gestures per object. Right-click cannot simultaneously be an unconditional erase and an unconditional menu on the same note: choose and teach one contract.

**Current:** channel button has a three-item `Response::context_menu`; step secondary-click clears a populated step, so screenshot 13 correctly shows no menu. Knobs have their own context menu. Tabs use dock's context callback. The mixer slot picker in 15 is a long stack of oversized buttons extending to the screen edge, not a compact, bounded menu.

**Fix:** retain FL-like right-click erase for step/note/clip editing, with right-drag erase and undo; expose properties through a separate object menu affordance or a modified right-click, explicitly documented. Channel button context: Piano roll, instrument, rename/color, clone, route, save preset, delete; steps: velocity via graph, not a conflicting menu. Clip's small menu triangle: make unique, rename/color, select source, delete; double-click opens editor. Mixer strip: rename/color, route, save/load state, reset; FX slot: replace, bypass, move, save/load preset, delete; browser row: preview/load/new/copy path/remove root as appropriate; dock tab: float/dock/close. Use `Response::context_menu`, `ui.menu_button` and `ScrollArea` with screen-edge clamping; no custom-position stack. Keyboard Escape dismisses innermost menu first; clicking elsewhere closes, never activates the underlying canvas on the same click. Validate with real interactions before promising egui provides every behavior automatically.

### Browser and asset model

**Evidence:** [01](screens/01-main-arrange.png), [14](screens/14-browser-files.png), `browser.rs::browser`, `files.rs::files_tab`, `load_file`, `drop_file_on_channel`. Current Project tab includes workspace, window, pattern and channel navigation, while Files tab displays user roots. Source supports arrow navigation, Enter, Escape, click audio to preview, double-click file to load, context actions, and drag targeting channels. FL distinguishes user locations and presets including plugin, channel, mixer, recorded, rendered and templates in its [user-file documentation](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/app_update.htm).

**Problem:** User explicitly wants this region for folders, presets and instruments; workspace/window controls dilute it. Files start as undifferentiated roots; discoverability of supported types, destinations, drag compatibility and selected channel is weak. A click to audition and double-click to load can trigger preview on the first click: validate audible interruption in a live run.

**Fix:** remove Project workspace/window/pattern lists from browser; put workspace choices in View, patterns in pattern picker, channels in rack. 220-point resizable tree, 26-point rows, folder disclosure, search with clear, add/remove roots and context actions. Organize compatible categories: Plugin database, Plugin presets, Channel presets, Mixer presets, Packs, Recorded, Rendered, Soundfonts, Templates and user folders. FL's Current project and Recent files are useful comparison categories but the user's constraint takes precedence: place them in File/project navigation, not the asset browser. Show type icons and an obvious preview state; arrows navigate, Left/Right collapse/expand, Enter opens or loads, Space previews. Drag sample to rack background creates sampler, onto channel replaces compatible source with explicit feedback, preset onto compatible instrument loads, mixer preset onto strip loads; incompatible targets reject visibly without mutation. Provide undo or confirmation for destructive replacement. Establish cancellation, drag threshold, pointer capture and no preview after drag. Native OS file drop and internal drag should share validation, but do not assume that support already exists.

### Channel rack

**Evidence:** 01–04, 12–13, 21; `rack.rs::rack`, `channel_strip`, `channel_label`, `paint_pad`, `graph_editor`, `rack_keys`. `toggle_step` supports Shift velocity cycling, right click clears active steps; channel secondary-click menu is already stock. Selection bar and miniature knobs are visually obscure. A wide four-beat frame uses room that could fit more channels or steps; low-contrast empty pads and tiny M labels make state hard to scan. Rack-selected, muted, soloed and playing need independent cues.

**Fix:** 28–30-point rows, 24×22 minimum step targets, subtle four-step groups, fixed 140–170-point identity region; scroll horizontally for long patterns and vertically for channels. LMB step sets, drag paints a consistent initial state; RMB clears/drag clears; Shift-click velocity is supplementary to a visible graph editor. Button opens instrument, right-click opens channel menu; mute LMB and solo RMB should have readable accessible names, plus keyboard actions. Piano-roll note preview opens roll. Retain custom painter for high-density timeline, not custom popup mechanics. [FL's desktop/Channel Rack introduction](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/boxinstaller/WebContent/FLStudio20_GettingStartedManual.pdf) shows the rack's role in the workflow.

### Piano roll

**Evidence:** 02, 03, 07, 25; `roll.rs`, `mod.rs::hint` and `Tool::key`. Visible notes are hairlines at the supplied zoom; keyboard is narrow and velocity lane almost empty. Large panel headers reduce pitch range. The screenshot cannot establish hit testing, select-box behavior, or undo semantics. FL's [piano-roll manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm) documents audition on keyboard, drag scrolling with middle mouse, snap, and Alt+wheel velocity.

**Fix:** 48–56-point keyboard, 14–18-point semitone rows default, clear octave labels, 60–100-point resizable velocity lane; independent X/Y zoom around pointer and scrollbars. Empty left-click creates snapped note; drag body moves selection, edges resize, Shift-drag duplicates, Ctrl-drag box-selects, right-click/drag deletes with undo, Alt temporarily bypasses snap. Keyboard audition must release on pointer-up/cancel and focus loss. Cursor signals move/resize; selection and ghost notes remain distinct without color alone. Allow tool/key shortcuts only when roll owns focus, no text field or modal owns input, and typing-piano policy is explicit. Custom canvas is justified for note interaction, while snap/tool/channel selectors should use `ComboBox`.

### Playlist

**Evidence:** [04](screens/04-playlist.png), `playlist.rs`, shell hints. Small clip previews and dark track separators are difficult to read; action buttons consume a second toolbar. FL's [Playlist manual](https://cluster.image-line.com/fl-studio-learning/fl-studio-online-manual/html/playlist.htm) describes shared pattern clips and configurable double-click editor behavior.

**Fix:** 100–140-point track header, 28–36-point default track height, adjustable zoom, ruler with bar and beat hierarchy, clearly visible playhead. LMB empty grid places the chosen pattern; drag moves; edge drag trims; Shift-drag duplicates linked clip; right drag erases with undo; double-click edits source; clip menu offers Make unique and names the consequence. Preserve drag offset, show snap preview, cancel on Escape. Consistently distinguish selection from playback and muted track. Test shared-data edits and undo across multiple instances.

### Mixer and plugin windows

**Evidence:** 05, 15, [19](screens/19-fx-window-builtin.png), [20](screens/20-mixer-plugin-slot.png), [21](screens/21-plugin-channel.png); `mixer.rs`, `plugins_ui.rs`, `instrument.rs`, `sampler.rs`. In 19 the effect editor is obscured by the mixer that launched it. 15's slot picker exceeds the available vertical space; the empty sampler in [06](screens/06-instrument-sampler.png) reserves a huge blank window. FL [mixer](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/mixer.htm) documents slot presets, including drag-to-copy compatible states.

**Fix:** 60–72-point mixer strips, 24-point labels, readable numeric level, track meters distinct from fader, scroll horizontally; selected FX panel 250–300 points with 26–30-point slots. Click selects strip, double-click fader resets to 0 dB, drag adjusts, right click opens contextual commands. Compact searchable bounded slot popup, categories and keyboard focus. Make launched editor frontmost, remember its position and avoid trapping it behind owner. Provide wrapper header with plugin name, preset previous/next, menu with load/save, bypass and detach/keep-on-top if supported; test native plugin windows independently for keyboard routing and lifetime. Use `Window`, `ScrollArea`, `ComboBox` and standard popup; customize meters and faders where their musical semantics justify it.

### Export and presets

**Evidence:** 23, `export.rs::export_window`, `menu.rs::menu_file`, `files.rs::load_file`, `instrument.rs`, `sampler.rs`. UI offers WAV/FLAC, pattern/song, tail, normalize and dither; File has MIDI export, and DWP import. An instrument preset is a different object from rendered audio or MIDI. A visible Load preset button alone does not establish save/round-trip support. FL's [export manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/fformats_save_export.htm) specifies WAV, MIDI and split mixer tracks, including constraints on master FX; its [mixer manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/mixer.htm) describes saving a slot preset.

**Fix:** separate Export audio, Export MIDI, Save channel/instrument preset, Save mixer track state, and Save FX preset. For audio: path with browse, source/range, WAV bit depth, sample rate, tail, normalization, dither, optional stems with clearly explained routing/master FX, estimated size, progress/cancel and errors. Disable Start when no format/path; never silently overwrite. For MIDI specify pattern/song and timing/channel mapping. For presets define a versioned KeyFrameXL format containing instrument/plugin identifier, plugin state and parameter metadata, sampler references with missing-file recovery, and channel settings; mixer state includes routing policy and effect ordering. Name format honestly: do not claim FL `.fst` compatibility without reading and writing FL's actual format. Save dialog supports overwrite confirmation; load validates type/version, preserves current state on failure, and supports undo. Offer copy/collect referenced samples for portability. Add round-trip tests for built-in sampler, missing assets, plugin unavailable, mixer chain and compatibility; make preset drag destinations visible.

## 3. Teenage Engineering and visual direction

The [OP-1 field](https://teenage.engineering/guides/op-1-field) combines dedicated controls with contextual screen feedback; [OP-XY](https://teenage.engineering/guides/op-xy) organizes performance and sequencing around its controls; [TX-6](https://teenage.engineering/guides/tx-6) compresses a mixer into a small physical surface; [EP-133](https://teenage.engineering/guides/ep-133) has large numbered pads and a physical fader. These are distinct objects with real hardware constraints. The transferable quality is clear correspondence of action, state, grouping, and tactile response. A software control cannot reproduce physical detents or tactile feedback; it can provide immediate visual response and predictable direct manipulation. FL's [mixer](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/mixer.htm) and [toolbar](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/toolbar_panels.htm) use hardware-derived channel strips, knobs and meters in a dense desktop workflow.

Ours (`theme.rs`, `kit.rs::raised`, `sunken`, `control`, `knob`, `fader`, `seg_text`) already has gradients, dark bevels, segment digits and red illuminated steps. The result in 01/05 is more uniform plastic framing than a hierarchy of distinct instruments: hundreds of tiny shiny elements and labels compete with actual notes. `docs/ui-rules.md` itself contains contradictory directions: 12-point minimum versus 10-point step labels, 'no modals' versus ordinary file/export decisions, and restrained depth versus decorative engraved labels and scanlines. Resolve in favor of legibility and the user's request for ordinary menus/dialogs.

**Direction:** matte graphite chassis, one fine top highlight and lower edge on controls, recessed time grids, brighter readable notes, 13–14-point body text, tabular numerals for values, color encoding for current selection/record/meter with shape or label reinforcement. Large, restrained hardware treatment belongs on transport, faders and instrument controls; menus, dialogs and file trees remain conventional. Knob drag gives immediate motion, numeric value and unit; double-click opens precise entry or reset according to one consistent rule. Use a small number of depths and a clear pressed state. Do not add screws, fake ventilation, microtext, scanlines, unnecessary shadows or illegible segment fonts; do not recreate tiny hardware just because hardware is small. Test contrast, focus and color blindness. `kit.rs::dropdown` already wraps `popup_below_widget`; avoid building new popup state machines. `kit::button`/`chips` redraw interactive controls and `knob_behaviour` implements input, text entry, context menu and focus; compare them against stock egui `Button`, `SelectableLabel`, `DragValue`, `Slider`, `ComboBox`, `Window` and `ScrollArea` before retaining. Their custom painting is not itself proof of broken behavior; keyboard, accessibility and popup ownership need live verification. Keep the bespoke timeline, meters and musical controls where stock widgets do not model the domain.

## 4. Implementation order

1. **P0, 2–4 days:** fix clipping, bounded scrolling and focus in shortcut/export/settings windows; prevent input leaking to the project; verify keyboard shortcuts and menu labels. Audit `Window`, `menu_button`, `context_menu`, `dropdown`, `chips` and manual keyboard handlers as wheel reinventions.
2. **P0, 3–5 days:** focus-aware command routing, typing-piano collision policy, gesture cancellation, undo and accessible labels; no destructive replacement without recovery.
3. **P0, 3–5 days:** reclaim editor space, resize targets, DPI/zoom persistence, 1366×768 and small-window behavior; keep `egui_dock` rather than replacing it.
4. **P1, 4–7 days:** asset-only browser with usable tree, explicit compatible drag/drop and audition state; move project/workspace controls elsewhere.
5. **P1, 5–10 days:** instrument/channel/FX/mixer preset schema and round-trip, then render/MIDI/stem export; plugin state and portability may add substantial scope.
6. **P1, 5–8 days:** rack/roll/playlist gesture contract, focus, zoom, note/clip selection and visual states, tested against real sessions.
7. **P1, 3–6 days:** bounded searchable mixer slot picker and window stacking; plugin wrapper and state lifecycle.
8. **P2, 3–5 days:** consistent material direction and type scale, strip unnecessary framing, tune controls and contrast after workflow changes.
9. **P2, 2–4 days:** complete FL shortcut comparison and in-app searchable reference; reconcile design documentation with the implemented behavior.

Estimates are intentionally broad and exclude full plugin-host compatibility, migration of old projects, packaging, and QA across Linux window managers. Before implementation, run an interaction matrix across mouse, touchpad, keyboard, mixed DPI and floating plugin windows; screenshots cannot verify these behaviors.
